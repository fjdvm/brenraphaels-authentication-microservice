## Authentication verification and cleanup

The initial staged login failure was an origin-configuration issue, not evidence that the supplied Administrator password was wrong: a provider probe returned HTTP 403, `INVALID_ORIGIN`, while the same credentials worked on the live Portal. With operator authorization, the exact staged origin was temporarily added to Neon Auth. Normal staged sign-in, sign-out, first-login password change, forgot-password, and reset-password then completed successfully. The temporary origin was removed afterward, restoring the original trusted-domain list containing only `https://br-auth-three.vercel.app`. The live production domain and deployment were not changed.

The test User was restored and issued fresh credentials for the password measurements. The new Temporary password email and the reset email arrived in the private test inbox. The reset email correctly targeted the configured production callback: after following the provider link, only the destination host was changed to the trusted staged host before the timed reset submission, retaining the token and signed email parameters. No application or provider callback configuration was changed. Reset was submitted while signed out, so its 4.817 s sample measures click-to-visible confirmation. The browser's reset-action fetch duration was separately 4.337 s, comparable in measurement boundary to #88's 7.529 s request-only observation. A subsequent sign-in with the new password reached the test User's Portal, verifying the reset.

The test Customer Profiles AccessGrant was revoked and `2026-PR-002` was soft-deleted again after all measurements. Its edit-access screen confirmed zero checked Modules before final deletion. Audit and grant history remain intact. The Administrator and test User measurement sessions were signed out, and the disposable inbox was removed after use. No database migration or seed operation was needed.

During initial failed sign-in attempts, runtime logs recorded `Failed to record audit event` with `TimeoutError` in `sin1`. This is an observed dependency failure, not proof that the region caused it. Later System Logs/My Logs reads returned events successfully, and all five final authentication flows completed. Several samples still exceed parent #87's targets; the region change improves these observations but does not establish that the remaining performance work is unnecessary.
